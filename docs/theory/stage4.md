# Этап 4. Безопасность, аудит и публикация

## 1. Авторизация

Минимальные требования:

- пароль хранится только в виде хэша;
- секреты хранятся в `.env`, а не в коде;
- защищённые маршруты доступны только после входа;
- выход завершает сессию или удаляет токен;
- тестовые пароли не используются в публичной среде.

Авторизация отвечает на вопрос «кто вошёл в систему». После успешного входа приложение должно хранить состояние пользователя в защищённой сессии или токене. Пароль при этом не сохраняется в открытом виде: в базе хранится только хэш, созданный специальной функцией.

Пример безопасного подхода:

```python
password_hash = generate_password_hash(password)
is_valid = check_password_hash(password_hash, entered_password)
```

Файл `.env` не публикуется в репозитории, потому что в нём могут быть секреты, строка подключения к базе данных и ключ сессии. Вместо него публикуется `.env.example` с безопасными примерными значениями.

## 2. Разграничение доступа

Проверка роли должна выполняться на backend. Скрыть кнопку на frontend недостаточно: пользователь может отправить запрос вручную.

Пример матрицы:

| Раздел | admin | manager | viewer |
|--------|:-----:|:-------:|:------:|
| Dashboard | чтение | чтение | чтение |
| Основные сущности | CRUD | CRUD | чтение |
| Пользователи | CRUD | нет | нет |
| Настройки | CRUD | нет | нет |
| Журнал действий | чтение | чтение | нет |

Матрица прав должна быть согласована с интерфейсом и серверной логикой. Если роль `manager` не может управлять пользователями, пункт меню можно скрыть, но маршрут `/admin/users` всё равно должен проверять роль и возвращать запрет доступа.

Пример серверной проверки:

```python
if current_user.role.code != "admin":
    abort(403)
```

## 3. Журнал действий

Журнал действий помогает понять, кто изменил данные.

Фиксируются:

- пользователь;
- действие: `create`, `update`, `delete`, `login`, `logout`;
- сущность;
- идентификатор записи;
- дата и время;
- IP-адрес или user-agent, если доступно;
- краткое описание.

Журнал особенно важен в административных системах, где несколько сотрудников меняют одни и те же данные. По журналу можно восстановить, кто удалил запись, кто изменил статус заказа или кто создал нового пользователя.

Пример записи журнала:

| Поле | Значение |
|------|----------|
| пользователь | `admin@example.local` |
| действие | `update` |
| сущность | `Product` |
| запись | `15` |
| описание | `Изменена цена товара "Клавиатура"` |

## 4. Тестирование

Проверяются сценарии:

1. вход с корректным и некорректным паролем;
2. доступ к закрытой странице без авторизации;
3. запрет действия для роли без прав;
4. создание, редактирование, удаление записи;
5. поиск, фильтры и пагинация;
6. появление записи в журнале действий.

Тестирование должно проверять не только «счастливый путь», но и ограничения. Например, нужно убедиться, что пользователь без роли `admin` не может открыть управление пользователями, а форма товара не сохраняет отрицательную цену. Такие проверки помогают обнаружить ошибки до демонстрации проекта.

Минимальный набор тестовых данных должен позволять проверить:

- вход под администратором и менеджером;
- пустой и заполненный список;
- успешное создание записи;
- ошибку валидации;
- запрет доступа;
- запись действия в журнал.

## 5. Публикация

Итоговый проект можно показать:

- локально через `npm run dev`, `flask --app run.py run --debug`, `python manage.py runserver`, `dotnet run` или аналог;
- в Docker Compose;
- на учебном сервере;
- на бесплатной платформе публикации, если это разрешено преподавателем.

Даже если проект демонстрируется локально, репозиторий должен быть оформлен так, чтобы другой человек мог повторить запуск. Для этого в README указываются стек, команды установки, настройка `.env`, создание базы данных, seed-данные и тестовые пользователи.

Итоговый пример проекта опубликован отдельно: [VKIP.UP.PM.08-projectWork](https://github.com/OlgaKraven/VKIP.UP.PM.08-projectWork). Методические материалы размещаются в репозитории [VKIP.UP.PM.08-method](https://github.com/OlgaKraven/VKIP.UP.PM.08-method).
