    Этап 1. Админ-панель и архитектура веб-приложения¶

    1. Что такое административная панель¶

    Административная панель — закрытая часть веб-приложения, через которую сотрудники управляют данными и настройками системы. В отличие от публичного сайта, админ-панель ориентирована на регулярную работу: быстрый поиск, таблицы, фильтры, формы, массовые операции, контроль ошибок и журнал действий.

    Например, в интернет-магазине публичный сайт показывает каталог и корзину, а админ-панель позволяет сотруднику добавить товар, изменить остаток на складе, обработать заказ и посмотреть, кто внёс изменение. В медицинской клинике админ-панель нужна для управления врачами, пациентами, расписанием и записями на приём.

    Главная особенность админ-панели — работа с данными должна быть безопасной и проверяемой. Пользователь не просто нажимает кнопки: система должна проверять его права, валидировать введённые данные, сохранять результат и фиксировать важные действия в журнале.

    2. Типовая структура¶

    Раздел Назначение
    Dashboard краткая статистика и быстрые действия
    Справочники категории, статусы, типы, услуги
    Основные данные предметные сущности: товары, записи, заказы, клиенты
    Пользователи учётные записи, роли, активность
    Журнал действий аудит изменений и входов
    Настройки параметры приложения

    Эти разделы образуют базовый рабочий цикл: пользователь входит в систему, видит dashboard, переходит к нужной таблице, находит запись через поиск или фильтр, редактирует данные, а система сохраняет событие в журнале.

    3. Архитектурные варианты¶

    Подход Когда подходит Пример
    Monolith MVC Удобно для учебного проекта, когда backend и страницы находятся в одном приложении Flask + Jinja2, Django, Laravel, ASP.NET Core MVC
    API + SPA Подходит, если frontend и backend разделяются и обмениваются JSON Express/FastAPI/Flask API + React/Vue
    Server-rendered + JS Подходит для CRUD-интерфейсов, где JavaScript нужен точечно Jinja2/Blade/Razor + небольшие scripts

    Для учебной практики важно выбрать такой подход, который позволит довести проект до рабочего состояния. Если команда уверенно работает с React и API, можно разделить frontend и backend. Если задача — быстрее собрать цельную админ-панель с авторизацией, CRUD и журналом действий, удобен MVC-подход.

    4. Состав проекта¶

    Минимальный проект должен иметь:

    • структуру папок backend/, frontend/ или единый MVC-проект;
    • конфигурацию через .env;
    • базу данных и seed-данные;
    • страницы входа и выхода;
    • защищённые маршруты;
    • dashboard;
    • CRUD-разделы;
    • журнал действий;
    • инструкцию запуска.

    Пример минимальной структуры MVC-проекта:

    web-admin-practice/
├── app/
│   ├── auth/          # вход, выход, текущий пользователь
│   ├── admin/         # dashboard и рабочие разделы
│   ├── templates/     # HTML-шаблоны
│   ├── static/        # CSS, JS, изображения
│   └── models.py      # модели данных
├── database/
├── seed.py
├── run.py
├── requirements.txt
└── README.md

    5. Flask как допустимый стек¶

    Flask можно использовать двумя способами:

    Вариант Описание
    Flask + Jinja2 сервер рендерит страницы админ-панели, JavaScript используется точечно
    Flask API + frontend Flask отдаёт JSON API, отдельный frontend на React/Vue/HTML+JS отвечает за интерфейс

    Для учебной практики особенно удобен вариант Flask + Jinja2 + SQLAlchemy, потому что он позволяет быстро собрать полноценную админ-панель: login, dashboard, CRUD-страницы, роли и журнал действий в одном проекте.

    В репозитории с примером проекта используется именно такой вариант: VKIP.UP.PM.08-projectWork.

    6. Роли пользователей¶

    Роли нужны, чтобы разные сотрудники видели разные разделы и могли выполнять только разрешённые действия.

    Роль Возможности
    admin полный доступ, управление пользователями и настройками
    manager управление основными данными без системных настроек
    viewer просмотр данных без редактирования

    Пример: менеджер интернет-магазина может редактировать товары и заказы, но не должен создавать новых администраторов или менять системные настройки. Проверка роли обязательно выполняется на сервере, потому что скрытая кнопка в интерфейсе не защищает маршрут от прямого запроса.

    7. Карта интерфейса¶

    Перед разработкой нужно составить карту админ-панели:

    Вход
└── Dashboard
    ├── Пользователи
    ├── Роли
    ├── Раздел 1 предметной области
    ├── Раздел 2 предметной области
    ├── Раздел 3 предметной области
    ├── Журнал действий
    └── Настройки

    Карта интерфейса помогает заранее увидеть, какие страницы нужны проекту, какие данные на них выводятся и какие права требуются для доступа. После карты проще проектировать базу данных и маршруты: каждый раздел админ-панели обычно соответствует таблице, модели, набору контроллеров и HTML-шаблонов.
